Architecture

The event bus is the design decision

Everything else follows from it. Market data arrives as events, signals are events, risk vetoes are events, orders and fills are events — and every one carries a schema-validated envelope and a reason code. Nothing calls anything else directly.

Property one

Golden-replay determinism

Replaying an identical input tape reproduces an identical event sequence, byte for byte. Most self-built trading systems lack this property, and without it a code change cannot be proven to have altered nothing outside its intent.

Property two

Hot-reloadable configuration

The running system reports 2,128 hot-reloadable parameters — they reload without a restart through a config → override → _on_reload spine. Without it, an automated calibration loop cannot tune a system that is currently running.

@dataclass(frozen=True, slots=True)
class EventEnvelope:
    schema: str
    event_id: str
    event_type: str
    event_version: int
    ts_event_ns: int          # when it happened
    ts_ingest_ns: int         # when we saw it
    seq: int                  # monotonic, per run
    source: str
    stream: str
    run_id: str
    session_id: str
    payload: Mapping[str, Any]
    reason_codes: tuple[str, ...] = ()
    payload_hash: str | None = None

frozen=True makes events immutable, so no downstream consumer can rewrite history, and payload_hash makes tampering detectable. The two timestamps are what make replay honest: separating when something happened from when the system saw it lets you reconstruct what the system knew at a moment, rather than what was true at that moment — the distinction that separates a realistic replay from an accidentally clairvoyant one. Reason codes propagate through the whole chain, so any decision can be traced back to the conditions that caused it.

Research loop

The system tunes itself — under gates

With 2,128 tunable parameters, the default outcome of an unconstrained search is an overfit, not a discovery. So the interesting engineering here is not the search. It's the gates.

01
Propose

Shadow search generates challenger parameter sets against the running champion.

02
Evaluate out-of-sample

Challengers are scored on data outside the window they were fitted on. Clearing that gate is a requirement, not a formality — it is the stage designed to reject overfits.

03
Canary

Survivors deploy at fractional allocation first, never straight to full size.

04
Gated promotion

Promotion requires a significance threshold, a cooldown window, and a per-day promotion cap.

Every cycle's verdict is written to an append-only decision ledger, so the parameter state of the system at any past moment is reconstructible — which matters more than it sounds, because a self-modifying system without an audit trail cannot be debugged after the fact.
