The idea

The platform is the product.
Strategies are pluggable.

Most self-built trading systems are a strategy with plumbing attached — when the strategy stops working, the system dies with it. Profit Pilot inverts that. The platform is permanent infrastructure whose job is to supervise, constrain, measure and retire the strategies running inside it. A sleeve that stops earning its risk budget gets throttled by the allocator and eventually refused promotion. The system is designed to outlive any idea in it.

Governed by construction

Risk is structural, not advisory

Eight independent governors compose into a single exposure multiplier. No signal reaches the broker without passing through all of them, and the console always reports which one is binding and why.

Reproducible by construction

Determinism is a first-class property

Every component speaks through schema-validated events on a deterministic bus. The same input tape replayed produces a byte-identical event sequence — which is what makes a bug reproducible three weeks later and a backtest auditable.

Adaptive by construction

The system tunes itself, under gates

~1,270 parameters are hot-reloadable and searchable by an automated research loop — but promotion requires clearing an out-of-sample gate, a fractional canary, a significance threshold and a cooldown.

Architecture

The event bus is the design decision

Everything else follows from it. Market data arrives as events, signals are events, risk vetoes are events, orders and fills are events — and every one carries a schema-validated envelope and a reason code. Nothing calls anything else directly.

Property one

Golden-replay determinism

Replaying an identical input tape reproduces an identical event sequence, byte for byte. This is the property most home-built trading systems silently lack, and without it you cannot prove that a code change altered nothing it shouldn't have.

Property two

Hot-reloadable configuration

Roughly 1,015 configuration values reload without a restart through a config → override → _on_reload spine. Without it, an automated calibration loop cannot tune a system that is currently running.

@dataclass(frozen=True, slots=True)
class EventEnvelope:
    schema: str
    event_id: str
    event_type: str
    event_version: int
    ts_event_ns: int          # when it happened
    ts_ingest_ns: int         # when we saw it
    seq: int                  # monotonic, per run
    source: str
    stream: str
    run_id: str
    session_id: str
    payload: Mapping[str, Any]
    reason_codes: tuple[str, ...] = ()
    payload_hash: str | None = None

frozen=True makes events immutable, so no downstream consumer can rewrite history, and payload_hash makes tampering detectable. The two timestamps are what make replay honest: separating when something happened from when the system saw it lets you reconstruct what the system knew at a moment, rather than what was true at that moment — the distinction that separates a realistic replay from an accidentally clairvoyant one. Reason codes propagate through the whole chain, so any decision can be traced back to the conditions that caused it.

Risk spine

Eight governors, composed

This is the part of the system I would defend most confidently, because it is designed to be correct rather than profitable. Risk controls don't need a forward-looking edge in order to work — they need to be structurally impossible to bypass. Each governor independently emits a clamp, and a clamp book aggregates them deterministically.

The aggregation rule is the design decision worth defending. Multipliers compose via min(), not by averaging, and the book fails closed — the most restrictive clamp wins. Averaging would let a permissive governor dilute a restrictive one, so a system that averages one "halt" against three "fine"s keeps trading. Taking the minimum means any single governor can stop the system on its own, and the console always names which one is binding.

"""Profit Pilot — Risk Clamp Book.

Multiple modules emit `risk.clamp` events (drawdown breaker, equity bands,
loss-day fingerprint, recovery parachute, etc.).

Execution needs a single coherent answer to questions like:
- "Am I allowed to open new positions right now?"
- "What risk multiplier applies to this sleeve/symbol?"
- "Is the system in exit-only mode?"

Design principles
-----------------
- *Fail closed*: the most restrictive clamp wins.
- Multipliers compose via `min()` (i.e., smallest multiplier dominates).
- Entry denial and exit-only flags follow highest-priority clamps.
- TTL is in bars and decays on `market.bar` ticks.
"""

The choice worth defending is composition by min() rather than by product or average. Averaging would let a permissive governor dilute a restrictive one — a system that averages one "halt" against three "fine"s keeps trading. Taking the minimum means any single governor can stop the system alone, and adding a ninth governor can only ever make the system safer, never riskier. That is the difference between a risk layer that is structurally safe and one that is merely behaviourally safe, and it is why the clamp book is one of the few places in this codebase where I would defend every line.

Research loop

The system tunes itself — under gates

With ~1,270 tunable parameters, the default outcome of an unconstrained search is an overfit, not a discovery. So the interesting engineering here is not the search. It's the gates.

01
Propose

Shadow search generates challenger parameter sets against the running champion.

02
Evaluate out-of-sample

Challengers are scored on data outside the fitting window. Most are declined here — that rejection rate is the feature.

03
Canary

Survivors deploy at fractional allocation first, never straight to full size.

04
Gated promotion

Promotion requires a significance threshold, a cooldown window, and a per-day promotion cap.

Every cycle's verdict is written to an append-only decision ledger, so the parameter state of the system at any past moment is reconstructible — which matters more than it sounds, because a self-modifying system without an audit trail is one you can never debug after the fact.

Module directory

39 locked modules

Every module is specified as a set of numbered "micros" — discrete, individually implementable behaviours catalogued in a ledger before any of them are written. The counts below are read from that ledger. The full ledger spans 1,823 catalogued micros across 54 module keys, of which 1,023 are implemented in code today; the 39 locked modules shown here account for 1,706 of those rows and 984 of the implementations. The remainder are specified, redirected, held for review, or explicitly retired.

The distinction is easy to abuse and worth being exact about. "1,800 features" is a number that would fit on a résumé; 1,023 implemented is the number that survives someone opening the ledger. Both are on this page for that reason.

Modules with catalogued detail expand. The capabilities listed inside are the ones the generated micro audit marks as built — not the full catalogue, and not the roadmap.

Risk is the largest category on every measure — nine modules, 42% of the catalogued surface of the locked set, and more code than strategy, intelligence and execution combined. That is not an accident of counting; it is where I think the difficulty in this problem actually lives.

Verification

Five layers of testing, before anything reaches a broker

A trading system is only as trustworthy as the machinery built to attack it. Profit Pilot carries five independent verification layers, each designed to catch a failure the others would miss.

Layer one

Historical backtesting

Every sleeve runs against historical bars through the same event bus the live engine uses — the identical code path, not a parallel research implementation. Commissions and slippage are modelled, and the report ships with its own data-quality header, including an explicit survivorship-bias notice when the dataset contains only currently-listed symbols.

Layer two

Deterministic blind replay

Any recorded session can be replayed bar for bar and must reproduce a byte-identical event sequence. This is what makes a bug from three weeks ago reproducible on demand, and it is how a code change is proven to have altered nothing it should not have. Golden-replay determinism runs in CI.

Layer three

Out-of-sample gating

Challenger parameter sets are scored on data outside the window they were fitted on, and the overwhelming majority are declined there. Only survivors advance — and they advance to a fractional canary, never straight to full size. A significance threshold, a cooldown window and a per-day promotion cap sit behind that.

Layer four

Monte Carlo & synthetic scenarios

The Ghost Synthetic Scenario Engine generates market conditions the historical record does not contain, and the Stress Scenario Lab pushes the portfolio through constructed shocks. Resampling turns single-path results into distributions, so a result is judged on its range rather than its one lucky history.

Layer five

Live forward testing

The system runs continuously in paper trading against a live brokerage API with real market data — real quotes, real order routing, real fill reconciliation. Forward testing is the only layer that cannot be overfitted, because the data has not been written yet. Every session is reconciled against the broker, and a fail-closed kill switch halts trading on any mismatch between what the engine believes it holds and what the broker reports.

Underneath all five sits an append-only decision ledger recording every cycle's verdict, so the exact parameter state of the system at any past moment can be reconstructed. A self-modifying system without an audit trail is one that can never be debugged after the fact — so the audit trail was built first.

What's next

Where it goes from here

Profit Pilot is in its first full testing year. The platform is built and running; the work now is deepening the research layer around it.

Walk-forward validation

Rolling out-of-sample evaluation across historical data. Tuning, backtest and challenger evaluation already exist as components — this is the orchestration layer that chains them into a continuous rolling protocol.

Execution-model refinement

Tightening the fill model so simulated execution tracks live execution more closely — queue position, partial fills under stress, and market impact.

Per-sleeve attribution

Measuring all six sleeves independently rather than in aggregate, so capital concentrates in the ones earning their risk budget.

Broader universe

The live symbol set is currently capped by the market-data plan. Lifting that cap widens the opportunity set the allocator can select from.
